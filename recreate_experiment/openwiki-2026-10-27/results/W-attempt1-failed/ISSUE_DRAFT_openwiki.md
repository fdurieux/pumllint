**Title:** `--init` aborts with "Could not restore …: ENOENT" when the first attempt on a nested page fails, so the retry never runs

### Summary

When a page worker's first attempt ends without `submit_page` (here a single transient provider error), `runPageAgent` restores the page snapshot before the retry. For a page that did not exist before the run and lives in a directory that does not exist yet (`/openwiki/architecture/…`, `/openwiki/concepts/…`, i.e. most pages of a fresh `--init`), the restore's `delete` fails with `ENOENT`. `isNotFoundBackendError` does not recognise that error, so the run aborts with `RepositoryRunError("invalid_state")`. The retry that `PAGE_WORKER_ATTEMPT_LIMIT = 2` provides never happens, and the original error is lost (see "Related").

### Environment

- openwiki 0.7.2 (also present at `main` `305599f`), deepagents 1.13.2 (as pinned)
- Node 22.22.0, Linux
- `openwiki --print --init`, provider `openai`, `gpt-5.6-terra`, `OPENWIKI_REASONING_EFFORT=xhigh`, `OPENWIKI_PAGE_CONCURRENCY=1`

### Observed

```
Could not restore /openwiki/architecture/data-layer.md: Error deleting '/openwiki/architecture/data-layer.md': ENOENT: no such file or directory, lstat '<repo>/openwiki/architecture'
```

Exit 1, no page written. `openwiki/.run.json` stays at `phase: "generating"` with every planned page `pending`; `.last-update.json` has `status: "interrupted"`. Seen on two runs out of two.

### Cause

1. `src/agent/repository-runner.ts` (`runPageAgent`, ~L898): after a non-submitted attempt, `await restoreRepositoryPage(run, snapshot)`.
2. For a new page `snapshot.markdown === null`, so `restoreRepositoryPageMarkdown` calls `run.backend.delete(path)` and tolerates only errors for which `isNotFoundBackendError` holds (`src/generation/repository-run.ts:622`):
   ```ts
   return error === "file_not_found" || error.includes("not found");
   ```
3. deepagents' `FilesystemBackend.delete` returns `"Error: '<p>' not found"` when the **file** is missing. In `virtualMode`, though, `resolveDeletePath` first `lstat`s each **parent** segment and lets the error propagate. With the parent missing, the outer catch returns `"Error deleting '<p>': ENOENT: no such file or directory, lstat …"`, which contains no `not found`. Reading deepagents 1.16.0, `assertRealPathWithinRoot(…, { includeLeaf: false })` still rethrows on a missing parent, so upgrading alone does not fix it.

### Minimal reproduction (no model call)

```js
// node repro.mjs <empty-dir>
import { FilesystemBackend } from "<openwiki>/node_modules/deepagents/dist/index.js";
const b = new FilesystemBackend({ rootDir: process.argv[2], virtualMode: true });
console.log(await b.delete("/absent.md"));
// { error: "Error: '/absent.md' not found" }
const r = await b.delete("/openwiki/architecture/data-layer.md");
console.log(r);
// { error: "Error deleting '/openwiki/architecture/data-layer.md': ENOENT: no such file or directory, lstat '<dir>/openwiki'" }
const isNotFoundBackendError = (e) => e === "file_not_found" || e.includes("not found"); // verbatim
console.log(isNotFoundBackendError(r.error)); // false -> RepositoryRunError("invalid_state")
```

### Suggested fix (either side)

- **OpenWiki:** treat `ENOENT` as not-found in `isNotFoundBackendError` (e.g. `|| error.includes("ENOENT")`), or skip the backend `delete` entirely when the snapshot recorded no file and nothing exists at the path.
- **deepagents:** in the delete path's parent walk, map `ENOENT` to the same `"… not found"` result the missing-file case returns.

### Related

The first attempt's error is discarded: `runPageAgent` keeps `outcome.error` only in a local, and nothing is logged under `--print`. So the user sees only the ENOENT above. Logging `outcome.error` locally showed the real first failure was `Error: 502 upstream request failed`, a transient gateway error on a long non-streaming `xhigh` call: exactly the case the retry exists for. Surfacing the attempt error (at least under `--debug`) would have made this diagnosable.
